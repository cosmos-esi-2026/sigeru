--- Incidente real durante la propia prueba (no fue un ensayo preparado) ----

administracion (10.0.2.2, el gateway NAT = la PC anfitriona) acumulo intentos

Es la prueba mas honesta posible de que la deteccion funciona: no fue un
ataque simulado, fue el propio jail por defecto reaccionando a fallos reales
de autenticacion contra el unico origen que existe en esta red NAT (la PC
que administra el servidor). El ban se levanto solo una hora... en realidad a
los ~9 minutos, por el "bantime" por defecto de Ubuntu (600 s), antes incluso
de escribir la politica propia. Es tambien la razon concreta, medida, de por
que el jail final necesita una lista blanca para el origen de administracion:
sin ella, el propio equipo puede quedar afuera de su servidor por errores de
tipeo, que es exactamente lo que paso acá.

--- Jail propio: config/fail2ban/sigeru.conf --------------------------------

$ sudo tee /etc/fail2ban/jail.d/sigeru.conf > /dev/null <<'EOF'
[DEFAULT]
ignoreip = 127.0.0.1/8 ::1 10.0.2.2
[sshd]
enabled  = true
maxretry = 3
findtime = 10m
bantime  = 1h
EOF
$ sudo fail2ban-client reload
OK

$ sudo fail2ban-client get sshd ignoreip
These IP addresses/networks are ignored:
|- 127.0.0.0/8
|- 10.0.2.2
`- ::1

--- Prueba manual de ban/desban sobre una IP sintetica (no la nuestra) ------

Se usa 198.51.100.23 (bloque TEST-NET-2, RFC 5737, reservado para
documentacion: no es una IP real de nadie) para demostrar que el mecanismo de
bloqueo funciona de verdad sin arriesgar la sesion de administracion.

$ sudo fail2ban-client set sshd banip 198.51.100.23
1

$ sudo fail2ban-client status sshd
Status for the jail: sshd
|- Filter
|  |- Currently failed:	0
|  |- Total failed:	8
|  `- Journal matches:	_SYSTEMD_UNIT=ssh.service + _COMM=sshd
`- Actions
   |- Currently banned:	1
   |- Total banned:	2
   `- Banned IP list:	198.51.100.23

$ sudo nft list set inet f2b-table addr-set-sshd
table inet f2b-table {
	set addr-set-sshd {
		type ipv4_addr
		elements = { 198.51.100.23 }
	}
}
(el ban de fail2ban no es solo un contador: es una regla real en nftables que
el kernel aplica sobre el trafico entrante al puerto 22)

$ sudo fail2ban-client set sshd unbanip 198.51.100.23
1
$ sudo nft list set inet f2b-table addr-set-sshd
table inet f2b-table {
	set addr-set-sshd {
		type ipv4_addr
	}
}
(vacia: el desbaneo tambien es real, no solo en el status)

alcanzables desde la red, MySQL nunca expuesto ni por bind address ni por
firewall), fail2ban vigilando sshd con una politica propia y probada -a

ban sintetico via nftables), y que la lista blanca de administracion
funciona sin abrir un agujero (el jail sigue activo para cualquier otro
origen).
